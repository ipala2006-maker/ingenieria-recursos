## Qué infraestructura usamos

- **Cloudflare:** aloja `estudiemos.ar`, sirve HTML, estilos y PWA desde Static Assets y enruta las APIs al Worker de servicios. El origen técnico `workers.dev` aún se usa para el despachador de notificaciones y compatibilidad nativa. No se debe retirar por confundirlo con Vercel. [Static Assets](https://developers.cloudflare.com/workers/static-assets/).
- **Supabase:** PostgreSQL, cuentas, sesiones, permisos, sincronización y cola. Su tarea `estudiemos-mobile-alarms` inicia el despacho hacia Cloudflare; este se comunica con Web Push o Firebase. Windows programa las alarmas localmente. El endpoint de Web Push declara disponibilidad; eso no confirma entrega a un dispositivo.
- **Brevo:** correo transaccional de Supabase Auth. Hay constancia previa de recuperación exitosa, pero esta auditoría no tuvo acceso a sus registros privados ni envió correos. **Google Drive:** guarda los archivos; Estudiemos guarda metadatos, enlaces y autorizaciones cifradas. **GitHub Actions:** ejecuta el respaldo cifrado y las pruebas de restauración.
- **Vercel:** no sirve tráfico activo ni cuenta como respaldo. El origen anterior responde como despliegue pausado; la tarea de retención está deshabilitada. El archivo `vercel.json` se usa localmente como fuente de cabeceras y CSP para Cloudflare, no como un servicio. Se conservan referencias históricas y reglas para clientes antiguos que no forman parte de la ruta normal.

## Piloto 20 → 50 → 100

1. **20 usuarios:** solo después de autorizar y verificar la publicación y pasar las pruebas reales de alta, invitación y notificación. Usar pocas cátedras de prueba, no promocionar Drive como abierto y repartir altas para observar SMTP. Registrar 2–3 días de uso y al menos un horario de alta demanda.
2. **50 usuarios:** ampliar solo si no se pierden borradores ni se cruzan datos, al menos 95% de intentos completos de alta/unión funcionan, el p95 de la API de alta/unión queda por debajo de 2 s sin contar correo ni CAPTCHA, y no hay 429/5xx sostenidos. Medir cola y retraso de alarmas reales en horario pico.
3. **100 usuarios:** mantener esos resultados, probar altas simultáneas desde el mismo Wi-Fi y medir una semana. Proyectar egreso total incluyendo respaldos y no ampliar si supera el 70% de la cuota mensual, si las solicitudes diarias se acercan al 70% del plan o si crecen los tiempos de cola, CPU y conexiones. Estos porcentajes y latencias son criterios internos, no SLA.

La [auditoría base](auditoria-lanzamiento-internacional-20261111.md) conserva el modelo de transferencia: 2,28 MB/mes de JSON de sincronización para dos dispositivos y 6,65 MB/mes en uso intensivo. El ahorro del 86% en Cátedras fue medido localmente. No incluyen todos los servicios ni demuestran capacidad de usuarios simultáneos o MAU reales.

**Dictamen:** candidato listo para revisión. **Piloto de 20: condicionado** a la publicación autorizada, verificación de permisos y una ronda física breve. **Difusión internacional masiva: todavía no.** Antes se necesitan métricas de 20/50/100, alta real en móviles, prueba de recuperación y un alcance claro para Drive y horarios entre países.
